# 11. 저장 형식 비교(JSONL vs CSV)와 10만 건 이상 확장 전략

이 문서는 두 가지 질문에 **측정한 숫자**로 답합니다.

1. 저장 형식으로 왜 CSV가 아니라 JSONL을 골랐나? (검색 · 편집성 · 원자성 · 성능)
2. 거래가 10만 건, 50만 건으로 늘면 어디가 먼저 느려지고, 무엇을 얼마의 비용으로 고치면 얼마나 빨라지나?

> 모든 숫자는 아래 [측정 환경](#측정-환경과-방법)에서 직접 잰 값입니다. "추정"이라고 적은 것만 계산으로 낸 값입니다.
> 컴퓨터마다 절대값은 달라도 **비율과 병목의 위치**는 거의 같습니다.

## 이 문서에서 배우는 것

- 저장 형식을 고를 때 비교해야 할 기준(검색, 편집성, 원자성, 성능)과 각 기준에서 JSONL과 CSV가 어떻게 다른지
- "파일이 커지면 느려진다"를 **어느 단계(읽기 / 파싱 / 객체 생성 / 정렬 / 재작성)가** 느린지로 나눠 측정하는 방법
- 명령별 병목의 원인을 코드에서 찾아 설명하는 방법
- 개선안마다 **비용(작업량·위험)**과 **효과(측정값)**를 함께 제시하고 우선순위를 정하는 방법

## 핵심 개념: 저장 형식을 고르는 네 가지 기준

### 1. 검색: 둘 다 "전체 훑기"다

JSONL과 CSV는 모두 **인덱스가 없는 텍스트 파일**입니다. "2023년 6월 거래"를 찾으려면 두 형식 모두 처음부터 끝까지 읽어야 합니다(O(n)).
검색 속도의 차이는 형식보다 **각 줄을 얼마나 싸게 걸러 내느냐**에서 납니다.

| 항목 | JSONL | CSV |
| --- | --- | --- |
| 한 레코드의 경계 | 항상 한 줄 | 따옴표 안 줄바꿈이 있으면 여러 줄 |
| 필드 찾기 | 키 이름이 줄 안에 있음 (`"date": "2023-06-...`) | 열 순서(헤더)를 알아야 함 |
| 파싱 전 bytes 선필터 | 쉬움: `b'"date": "2023-06' in line` | 가능하지만 열 위치에 의존, 여러 줄 레코드에서 깨짐 |
| 중첩 값(태그 목록) 검색 | 배열 그대로 (`["점심", "회사"]`) | `"점심,회사"` 문자열을 다시 쪼개야 함 |

JSONL은 줄 하나가 곧 레코드 하나라서 **"파싱하기 전에 원문에서 먼저 거르기"**가 안전합니다.
뒤의 [개선안 B](#b-원문-bytes-선필터-선택적-검색-20배)에서 이 성질로 월 검색을 20배 빠르게 만듭니다.

### 2. 편집성: 사람이 고칠 때 무엇이 깨지나

| 상황 | JSONL | CSV |
| --- | --- | --- |
| 텍스트 편집기로 한 건 고치기 | 해당 줄만 고치면 됨. 키 이름이 있어 뜻을 알 수 있음 | 몇 번째 열이 무엇인지 헤더와 맞춰 봐야 함 |
| 엑셀로 열기 | 불편함 (한 칸에 JSON 한 줄) | **편함**. 사람이 보기 가장 좋음 |
| 엑셀로 저장하기 | 해당 없음 | 날짜가 `2026/10/01`로, 긴 숫자가 지수 표기로 바뀌거나, 한국어 Windows에서 cp949로 저장될 위험 |
| 필드 추가(스키마 변경) | 새 키를 추가만 하면 됨. 옛 줄은 기본값으로 읽음 (`from_record`) | 헤더를 바꾸고 **모든 행**의 열 개수를 맞춰야 함 |
| 메모에 쉼표·따옴표·줄바꿈 | `json.dumps`가 이스케이프 | 큰따옴표로 감싸고 `"`를 `""`로 바꿔야 함. 손으로 고치다 자주 깨짐 |
| 잘못 고친 줄의 영향 | **그 줄만** 못 읽음 (경고 후 건너뜀, 원문 보존) | 따옴표 하나가 빠지면 **그 뒤 모든 행**이 한 칸으로 합쳐질 수 있음 ([07 문서](07-csv-import-export.md)의 `strict=True` 참고) |

결론: **사람이 보고 엑셀로 주고받기에는 CSV**, **프로그램이 안전하게 저장하고 사람이 가끔 고치기에는 JSONL**이 낫습니다.
그래서 이 프로젝트는 저장은 JSONL, 교환(`import`/`export`)은 CSV로 역할을 나눴습니다.

### 3. 원자성: 형식이 아니라 "쓰는 방법"이 보장한다

먼저 오해 하나를 짚습니다. **JSONL도 CSV도 형식 자체로는 원자성을 보장하지 않습니다.**
원자성은 "임시 파일에 쓰고 `fsync` 후 `os.replace`로 교체"하는 **쓰기 방법**([02 문서](02-file-storage.md)의 `AtomicWriter`)이 만듭니다.
이 방법은 두 형식에 똑같이 쓸 수 있습니다.

형식이 차이를 만드는 곳은 **"쓰다가 끊긴 줄을 알아챌 수 있느냐"**입니다. 추가(append) 도중 전원이 나가 마지막 줄이 잘렸다고 해 봅시다.

```text
원래 쓰려던 줄 (JSONL): {"id": 5, "type": "expense", "date": "2026-10-01", "amount": 12000, "category": "food"}
잘린 줄       (JSONL): {"id": 5, "type": "expense", "date": "2026-10-01", "amount": 12
→ json.loads 실패 → "손상된 줄"로 감지, 경고 후 건너뜀 (데이터가 틀리게 읽히지 않음)

원래 쓰려던 행 (CSV): 2026-10-01,expense,food,12000,점심
잘린 행       (CSV): 2026-10-01,expense,food,12
→ 열 4개짜리 정상 행으로 읽힘 → 금액 12원짜리 거래가 "조용히" 생김
```

직접 확인할 수 있습니다.

```bash
python3 -c "import json; json.loads('{\"id\": 5, \"amount\": 12')"
```

```text
json.decoder.JSONDecodeError: Expecting ',' delimiter: line 1 column 23 (char 22)
```

```bash
python3 -c "import csv, io; print(list(csv.reader(io.StringIO('2026-10-01,expense,food,12'))))"
```

```text
[['2026-10-01', 'expense', 'food', '12']]
```

JSONL은 줄 끝에 닫는 `}`가 있어야 올바른 줄이라 **잘림이 스스로 드러납니다(self-delimiting)**. CSV는 그렇지 않습니다.
그래서 이 프로젝트의 "끊긴 마지막 줄 감지·복구"([02 문서](02-file-storage.md)의 `JsonlFile.append`)는 JSONL이라서 단순하게 구현할 수 있었습니다.

### 4. 성능: 형식보다 "파이썬 객체 만들기"가 비싸다

50만 건 파일을 처음부터 끝까지 읽으면서, 단계마다 얼마가 드는지 재 봤습니다.

| 단계 (50만 건, 3회 중 최솟값) | 누적 시간 | 해당 단계만 |
| --- | --- | --- |
| ① 파일에서 줄을 bytes로 읽기만 | 0.026s | 0.026s |
| ② + `json.loads` | 0.637s | 0.611s |
| ③ + `Transaction.from_record` (검증, 날짜 파싱, dataclass 생성) = 현재 `iter_all()` | **1.771s** | **1.134s** |
| ④ CSV: `csv.reader`만 | 0.210s | - |
| ⑤ CSV: `DictReader` + 형 변환 + `from_record` | **1.623s** | - |

| 파일 크기 (50만 건, 같은 내용) | 크기 |
| --- | --- |
| JSONL (`transactions.jsonl`) | 85.8MB |
| CSV (같은 8개 필드) | 38.6MB |
| SQLite (인덱스 1개 포함) | 47.5MB |

읽어 낼 수 있는 사실은 세 가지입니다.

1. **디스크 읽기는 병목이 아닙니다.** 85.8MB를 줄 단위로 읽는 데 0.03초입니다(운영체제 캐시가 데워진 상태).
2. **CSV 파싱(0.21s)이 JSON 파싱(0.61s)보다 약 3배 빠릅니다.** CSV는 키 이름이 없어 파일이 2.2배 작고, 값이 모두 문자열이라 단순하기 때문입니다.
3. 그런데 **최종 차이는 8%뿐입니다(1.77s vs 1.62s).** 전체 시간의 64%가 형식과 상관없는 ③ "검증하고 객체를 만드는" 단계에서 들기 때문입니다.
   CSV는 오히려 `int()` 변환, 태그 쪼개기 같은 일을 직접 해야 합니다.

> 성능 결론: 저장 형식을 CSV로 바꿔서 얻는 속도는 **10% 미만**입니다. 대신 위에서 본 편집 안전성과 잘림 감지를 잃습니다.
> 큰 데이터에서 빨라지려면 형식을 바꾸는 것보다 **"필요 없는 줄은 객체로 만들지 않기"**가 훨씬 효과적입니다(개선안 A·B·E).

### 종합 비교

| 기준 | JSONL | CSV | 이 프로젝트에서의 비중 |
| --- | --- | --- | --- |
| 검색 | 전체 훑기. bytes 선필터가 안전함 | 전체 훑기. 선필터는 열 위치에 의존 | 중 |
| 편집성 (프로그램 + 가끔 손 편집) | 키 이름이 있고 줄 단위로 고장이 격리됨 | 따옴표 하나로 뒤쪽 전체가 깨질 수 있음 | 상 |
| 편집성 (엑셀로 보기) | 불편 | **좋음** | 하 (export로 해결) |
| 원자성 (끊긴 쓰기 감지) | **잘린 줄이 스스로 드러남** | 잘린 행이 정상처럼 읽힐 수 있음 | 상 ("데이터가 안전한 작은 서비스") |
| 스키마 변경 | 키 추가만 하면 됨 | 모든 행 수정 | 중 |
| 파싱 속도 | 느림 (0.61s / 50만 건) | 빠름 (0.21s) | 하 (전체의 8% 차이) |
| 파일 크기 | 큼 (2.2배) | 작음 | 하 (50만 건에 86MB) |

**저장은 JSONL, 교환은 CSV**라는 선택의 근거가 이것입니다.

| 항목 | 값 |

| 컴퓨터 | Apple M6, 메모리 32GB, macOS 27.0.1, APFS SSD |
| Python | 3.9.6 (macOS 기본) |
| 데이터 | 10만 건 17.0MB, 50만 건 85.8MB. 2020-01 ~ 2025-06에 고르게 분포, 지출 90% / 수입 10%, 메모의 1/7에 "점심" 포함 |
| 측정 방식 | 명령마다 **새 프로세스**로 실행 (`python3 -m budget_app ...`). 시간은 벽시계 시간, 메모리는 최대 RSS(`os.wait4`). 파이썬 시작 비용 약 0.07초가 포함됨 |

데이터 생성 스크립트입니다. 실제 데이터 폴더가 아닌 곳에 만드세요.

```python
# gen.py — 사용법: python3 gen.py 100000 /tmp/budget-big
import datetime as dt, json, os, random, sys

n, folder = int(sys.argv[1]), sys.argv[2]
os.makedirs(folder, exist_ok=True)
random.seed(1)
start = dt.date(2020, 1, 1)
spend = ["food", "transport", "rent", "utilities", "shopping", "health"]
with open(f"{folder}/transactions.jsonl", "w", encoding="utf-8") as f:
    for i in range(1, n + 1):
        kind = "income" if i % 10 == 0 else "expense"
        f.write(json.dumps({
            "id": i, "type": kind,
            "date": (start + dt.timedelta(days=i * 2000 // n)).isoformat(),
            "amount": random.randint(1000, 90000),
            "category": "salary" if kind == "income" else random.choice(spend),
            "memo": f"메모 {i} 점심" if i % 7 == 0 else f"메모 {i}",
            "tags": ["회사"] if i % 5 == 0 else [],
            "created_at": "2026-10-19T00:00:00",
        }, ensure_ascii=False) + "\n")
with open(f"{folder}/meta.jsonl", "w") as f:
    f.write(json.dumps({"key": "transaction", "value": n}) + "\n")
```

```bash
python3 gen.py 100000 /tmp/budget-big
```

```bash
time python3 -m budget_app --data-dir /tmp/budget-big list --limit 20
```

카테고리 파일이 없으면 첫 실행에서 기본 카테고리가 자동으로 만들어집니다.

| 명령 | 10만 건 | 50만 건 | 최대 메모리 (50만 건) | 파일 전체 읽기 횟수 |
| --- | --- | --- | --- | --- |
| `category list` (카테고리별 사용 건수) | 0.44s | 1.88s | 22MB | 1 |
| `list --limit 20` | 0.49s | 2.06s | 22MB | 1 |
| `search --month 2023-06` (결과 약 1.5%) | 0.49s | 2.05s | 33MB | 1 |
| `search --q 점심 --limit 20` | 0.46s | 1.98s | 22MB | 1 |
| `search --q 점심` (limit 없음, 결과 14%) | 0.70s | 3.26s | 132MB | 1 |
| `search` (조건 없음 = 전체를 정렬해 출력) | 2.07s | **10.80s** | **787MB** | 1 |
| `summary --month 2025-06` | 0.44s | 1.84s | 22MB | 1 |
| `add` (거래 1건) | 0.43s | 1.88s | 22MB | 1 (+ 추가 1줄) |
| `update --id N` | 0.67s | 2.98s | 22MB | 2 (+ 재작성) |
| `delete --id N --yes` | 0.85s | 3.86s | 22MB | 3 (+ 재작성) |
| `category remove shopping --replace-with etc` | 0.94s | 4.24s | 22MB | 3 (+ 재작성) |
| `export --from 2020-01-01` (전체 내보내기) | 0.59s | 2.83s | **378MB** | 1 |
| `import` (위에서 내보낸 CSV를 다시 가져오기) | 1.25s | 5.88s | 22MB | 2 (+ 복사) |
| `backup` | 0.20s | 0.64s | 22MB | 0 (압축만) |

### 숫자로 보는 성장 법칙

- 파일을 한 번 훑는 명령은 대략 **`0.07s + 3.7μs × 건수`**입니다. 50만 건에서 약 1.9초, **100만 건이면 약 3.8초(추정)**입니다.
- 메모리는 `list --limit`, `summary`, `update`/`delete`가 **건수와 상관없이 22MB**로 일정합니다. 스트리밍 설계([03 문서](03-generators-streaming.md))가 제 역할을 하고 있습니다.
- 반대로 **결과 전체를 모아 정렬하는 두 경로**(`--limit` 없는 `search`, `export`)는 메모리가 건수에 비례합니다.
  50만 건에서 787MB이므로, 100만 건이면 1.5GB를 넘습니다(추정).

## 병목 분석

### S1. 조회 명령 (`list`, `search`, `summary`, `category list`): 줄마다 객체를 만든다

한 번 훑는 데 드는 1.8초 중 **1.1초가 `Transaction.from_record`**, 0.6초가 `json.loads`, 디스크는 0.03초입니다.
`list --limit 20`은 결과로 20건만 필요한데도 50만 건 전부를 검증된 `Transaction` 객체로 만든 뒤 `heapq.nlargest`에 넣습니다.
`search --month`는 결과가 1.5%뿐인데도 나머지 98.5%를 객체로 만들고 버립니다.

```mermaid
flowchart LR
    A["줄 읽기<br/>0.03s"] --> B["json.loads<br/>0.61s"] --> C["from_record<br/>1.13s"] --> D["조건 검사"] --> E["nlargest / 집계"]
    style C fill:#f9d5d3
    style B fill:#fde8c8
```

**원인:** 걸러 내기(`SearchCriteria.matches`)가 **객체를 다 만든 뒤에** 일어납니다. 대부분의 비용이 "버려질 줄"에 쓰입니다.

### S2. `--limit` 없는 `search`와 `export`: 결과 전체를 객체로 메모리에 올린다

`newest_first(items, limit=None)`와 `oldest_first`는 정렬하려고 **모든 결과를 `Transaction` 리스트로 모읍니다.**
50만 건이 결과가 되면 객체만 수백 MB이고, 화면 출력용 표 문자열까지 만들어 787MB가 됩니다.
측정해 보면 정렬 단계만 따로 떼어도 객체 전체 정렬은 339MB, `(날짜, 순번, 바이트 오프셋)` 키만 정렬하면 86MB였습니다(`tracemalloc` 기준).

**원인:** 정렬에 필요한 것은 날짜와 순서뿐인데 레코드 전체를 들고 있습니다. 또, 화면에 50만 줄을 한 번에 그리는 것 자체가 사람에게 쓸모가 없습니다.

### S3. `add`: 한 줄을 쓰려고 파일 전체를 읽는다

추가 자체(append + fsync)는 1ms도 걸리지 않습니다. 그런데 `add`가 50만 건에서 1.88초 걸립니다.
`LedgerService.add`가 id를 정하려고 `self._transactions.max_id()`를 부르고, 이 함수가 **파일 전체를 디코드**하기 때문입니다(측정 1.75초).
이것은 `meta.jsonl`이 사라지거나 뒤처져도 id가 겹치지 않게 하는 안전장치입니다([02 문서](02-file-storage.md)). 안전하지만 매번 지불하기엔 비쌉니다.

### S4. `update` / `delete`: 같은 파일을 2~3번 읽고, 전체를 다시 쓴다

`delete --id 3 --yes` 한 번에 일어나는 일입니다.

| 단계 | 하는 일 | 파일 읽기 |
| --- | --- | --- |
| `cmd_delete` | 삭제할 거래를 보여 주려고 `ledger.get(id)` | 1회 (중간에 찾으면 멈춤) |
| `LedgerService.delete` | 다시 `self.get(tx_id)`로 존재 확인 | 1회 |
| `TransactionRepository.delete` | `JsonlFile.rewrite`: 전체를 읽으며 임시 파일에 다시 쓰고 교체 | 1회 + 85MB 쓰기 + fsync |

재작성 한 번만 2.07초입니다(측정). 원자성을 위해 **한 줄을 지우려고 85MB를 다시 쓰는 구조**라서,
`update`/`delete`는 건수에 정비례해서 느려집니다. 이것이 "텍스트 파일 + 전체 재작성" 방식의 근본 한계입니다.

### S5. `category remove --replace-with`와 `import`

- `category remove --replace-with`: 사용 건수를 세는 훑기, 거래 재작성, 반복 규칙 재작성이 차례로 일어납니다(4.24s).
- `import`: id를 정하는 `max_id()` 훑기, `staged_append`의 기존 파일 전체 복사, 그리고 행마다 검증(`parse_csv_row`) 후 `Transaction`을 만듭니다.
  50만 행을 가져오는 데 5.88초이고, 행당 약 10μs입니다. 일괄 작업이고 가끔 실행하므로 우선순위는 낮습니다.

### 병목이 아닌 것

- **파이썬 시작 비용**: 0.07초입니다. 문제가 아닙니다.
- **디스크 I/O와 fsync**: 읽기 0.03초, 한 줄 추가 1ms 미만입니다.
- **`backup`**: zip 압축이 C 코드라서 50만 건도 0.64초입니다.
- **메모리 (조회·수정 경로)**: 스트리밍 덕분에 50만 건에서도 22MB입니다.

## 개선 방안: 비용과 효과

비용은 "이 프로젝트 구조를 아는 학습자 한 명" 기준의 작업 시간과 변경 코드 양으로 적었습니다.
효과는 프로토타입으로 **직접 잰 값**이고, 잴 수 없었던 것만 "추정"이라고 표시했습니다.

### A. `max_id`를 O(1)로: meta 값 + 파일 끝만 확인 (`add` 약 18배)

**무엇을:** id 발급 때 파일 전체를 읽지 않습니다. `meta.jsonl`의 값과 **파일 끝 4KB에 있는 마지막 몇 줄의 id**만 비교합니다.
id는 늘 증가하며 끝에 추가되므로, 사람이 손으로 편집하지 않았다면 마지막 줄의 id가 최댓값입니다.
안전장치는 남깁니다. 끝에서 읽은 id가 meta 값보다 크면(사람이 편집했다는 신호), 그때만 전체 훑기로 되돌아갑니다.

```python
# 프로토타입: 파일 끝 4KB만 읽어 마지막 줄들의 id 확인
with open(path, "rb") as h:
    h.seek(0, 2)
    h.seek(max(0, h.tell() - 4096))
    tail = h.read().splitlines()[1:]  # 첫 조각은 잘린 줄일 수 있어 버린다
last_ids = [json.loads(line)["id"] for line in tail if line.strip()]
```

| 비용 | 효과 (50만 건) | 위험과 대응 |
| --- | --- | --- |
| 0.5일, 약 30줄 (`SequenceStore`, `TransactionRepository`), 테스트 3~4개 | `max_id` 1.75s → 0.0004s. **`add` 1.88s → 약 0.1s (추정)** | 손 편집으로 id 순서가 뒤섞이면 끝만 봐서는 놓칠 수 있습니다. "meta보다 큰 id가 끝에 보이면 전체 훑기"와 "중복 id는 `get`으로 한 번 더 확인"으로 막습니다 |

### B. 원문 bytes 선필터: 선택적 검색 약 20배

**무엇을:** `json.loads`와 `from_record` **전에** 원문 bytes에서 먼저 거릅니다.
이 프로그램이 저장한 줄은 형식이 일정하므로(`json.dumps`의 기본 구분자, ISO 날짜) `"date": "2023-06`라는 바이트열이 있는지만 보면 됩니다.
통과한 줄만 디코드하고, 디코드한 뒤에도 **원래 조건(`SearchCriteria.matches`)으로 다시 검사**합니다. 선필터는 "후보 줄이기"만 하는 것입니다.

```python
key = b'"date": "2023-06'
for line in handle:                 # bytes
    if key not in line:             # 98.5%는 여기서 버린다 (파싱 비용 0)
        continue
    tx = Transaction.from_record(json.loads(line))
    if criteria.matches(tx):        # 최종 판단은 항상 원래 조건으로
        yield tx
```

| 비용 | 효과 (50만 건, 결과 7,500건으로 일치 확인) | 위험과 대응 |
| --- | --- | --- |
| 1일, 약 60줄 (`JsonlFile`에 선택적 `prefilter` 인자, `SearchCriteria`가 bytes 키를 만들어 줌), 테스트 5개 | 월 검색 **2.22s → 0.11s (20배)**. `summary --month`도 같은 원리로 약 20배 (추정) | **놓치는 줄(false negative)이 없어야** 합니다. 손으로 고쳐 공백이 달라진 줄(`"date":"2023-06"`)은 선필터에서 빠질 수 있습니다. 날짜·타입처럼 이 프로그램이 형식을 정하는 필드에만 쓰고, 메모 키워드(이스케이프될 수 있는 문자 포함)는 bytes 비교에서 제외하거나 이스케이프 형태로 바꿔 비교합니다 |

### C. `update`/`delete`의 중복 훑기 제거: 약 1.8배

**무엇을:** 재작성 콜백(`first_match`)이 바꾸거나 지운 거래를 기록해 돌려주게 합니다. 그러면 `LedgerService` 안의 `get()`이 필요 없어지고,
"존재 확인 + 변경"이 **재작성 한 번**으로 끝납니다. 재작성이 아무것도 바꾸지 못하면 그때 `NotFoundError`를 던집니다.

- `update`: 지금은 `get()`(중간 id면 파일 절반) + 재작성입니다. 바꾸기 전 값은 콜백이 기록하므로 재작성 1회면 됩니다.
- `delete --yes`: 확인 질문이 없으니 미리 보여 줄 필요도 없습니다. 지운 거래를 **삭제한 뒤** 출력하면 재작성 1회입니다.
- `delete`(확인 질문 있음): 질문 전에 내용을 보여 줘야 하므로 `cmd_delete`의 `get()` 1회는 남습니다.

| 비용 | 효과 (50만 건, 중간 id 기준) | 위험과 대응 |
| --- | --- | --- |
| 0.5일, 약 40줄 (`first_match`가 대상 기록, `LedgerService.update/delete`, `cmd_delete`의 출력 순서), 기존 테스트로 회귀 확인 | `delete --yes` 3.86s → 약 2.1s, 확인 질문 있는 `delete` → 약 3.0s, `update` 2.98s → 약 2.1s (재작성 1회 측정값 2.07s와 중간까지의 `get()` 약 0.9s로 계산한 추정) | 거의 없음. `--yes`일 때 "삭제할 거래" 대신 "삭제한 거래"를 보여 주도록 출력 문구만 바꿉니다 |

### D. 지연 디코드(lazy decode): `list --limit` 10배, 정렬 메모리 1/4

**무엇을:** 정렬에 필요한 **날짜만 원문에서 잘라 내고**, `(날짜, 순번, 바이트 오프셋)` 튜플로 `heapq.nlargest`/정렬을 합니다.
최종 결과가 정해진 뒤에 그 오프셋으로 `seek()`해서 **결과 줄만** 디코드합니다.

```python
KEY = b'"date": "'
def keys(handle):
    offset = 0
    for index, line in enumerate(handle):
        p = line.find(KEY)
        yield (line[p + 9:p + 19], index, offset)   # b"2025-06-30" 같은 10바이트
        offset += len(line)

top = heapq.nlargest(20, keys(handle))              # 객체는 하나도 만들지 않음
for _, _, offset in top:
    handle.seek(offset)
    yield Transaction.from_record(json.loads(handle.readline()))
```

| 비용 | 효과 (50만 건) | 위험과 대응 |
| --- | --- | --- |
| 1~1.5일, 약 80줄 (`JsonlFile`에 오프셋 순회, `newest_first`/`oldest_first`의 키 기반 버전), 테스트 6개 | `list --limit 20` 디코드 단계 **1.91s → 0.19s (10배, 같은 결과 확인)**. 정렬 메모리 339MB → 86MB. `export` 최대 메모리 378MB → 약 100MB (추정) | 날짜 키를 못 찾는 줄(손상·손 편집)은 기존 방식으로 디코드해 처리합니다. 오프셋을 쓰는 동안 파일이 바뀌면 안 되므로 같은 명령 안에서만 씁니다 |

함께 할 일: `--limit` 없는 `search`는 결과가 수십만 건일 때 화면에 다 그리지 말고, **기본 상한(예: 1,000건)과 안내 문구**를 둡니다.
비용 0.2일, 효과: 787MB·10.8초가 걸리던 실수성 명령이 `--limit 1000` 수준(약 2초, 30MB, 추정)으로 바뀝니다.

### E. 객체 생성 비용 줄이기: 약 20~30% (추정)

**무엇을:** `from_record`의 비용(1.13s/50만 건)을 줄입니다. 예: 날짜 형식 정규식 검사 후 `fromisoformat`를 한 번 더 하는 이중 검사를 하나로 합치기,
`__post_init__` 검사와 `_get_*` 검사의 중복 줄이기, Python 3.10 이상이면 `@dataclass(slots=True)`로 객체를 가볍게 만들기.

| 비용 | 효과 | 위험과 대응 |
| --- | --- | --- |
| 0.5~1일, 약 40줄, 기존 검증 테스트가 그대로 통과해야 함 | 전체 훑기 20~30% 단축 (추정). A·B·D를 하고 나면 디코드하는 줄 자체가 적어져 효과가 작아짐 | 검증을 빼면 "신뢰할 수 없는 파일 데이터"가 들어옵니다. **검증은 줄이지 말고 중복만 줄이는** 것이 원칙입니다. 외부 라이브러리(`orjson` 등)는 "표준 라이브러리만" 조건 때문에 이 과제에서는 쓰지 않습니다 |

### F. 월별 파일 분할(partitioning): 월 단위 작업 약 40배 (추정)

**무엇을:** `transactions.jsonl` 하나 대신 `transactions/2026-10.jsonl`처럼 **월마다 파일**을 둡니다.
`summary --month`와 `search --month`는 파일 하나만 읽고, `update`/`delete`는 **그 달 파일만 재작성**합니다.
id로 찾으려면 "id → 월" 작은 인덱스 파일이 하나 더 필요합니다.

| 비용 | 효과 (측정 데이터: 50만 건이 66개월에 분산 → 월당 약 7,600건) | 위험과 대응 |
| --- | --- | --- |
| 2~3일, 약 300줄 (저장소 계층 재설계, 기존 파일 이전(migration) 명령, 백업 대상 변경), 테스트 15개 이상 | 월 요약·월 검색 1.84s → 약 0.05s. 한 건 수정·삭제의 재작성 2.07s → 약 0.03s (파일 크기 1/66 기준 추정). 날짜를 바꾸는 `update`는 두 파일을 써야 함 | 여러 파일에 걸친 변경(날짜 변경, 카테고리 일괄 변경)은 원자성이 파일 단위로 쪼개집니다. "새 파일 먼저 쓰고 옛 파일에서 지우기" 순서와 복구 절차를 설계해야 합니다. 기간 전체 조회는 여전히 모든 파일을 읽습니다 |

### G. SQLite로 저장소 교체: 대부분 작업이 1ms 단위

**무엇을:** 표준 라이브러리 `sqlite3`으로 `TransactionRepository`를 다시 구현합니다. 날짜에 인덱스를 두고, 수정은 트랜잭션으로 묶습니다.
계층을 나눠 둔 덕분에 **바꿀 곳은 `storage.py`와 객체를 조립하는 `context.py`**, 그리고 데이터 파일을 직접 다루는 `backup.py`뿐입니다.
서비스와 CLI는 그대로입니다([01 문서](01-architecture.md)).

| 작업 (50만 건) | 현재 JSONL | SQLite (측정) |
| --- | --- | --- |
| 최신 20건 | 2.06s (명령 전체) / 1.91s (디코드) | **<1ms** (`ORDER BY date DESC LIMIT 20`, 인덱스) |
| 월 요약 (카테고리별 합계) | 1.84s | **1ms** (`WHERE date BETWEEN ... GROUP BY`) |
| 메모 키워드 검색 (인덱스 없음, 전체 훑기) | 1.98s | **18ms** (C로 구현된 훑기) |
| 1건 수정 + 커밋 | 2.98s | **<1ms** |
| 최초 이전(JSONL → SQLite, 1회) | - | 0.82s |
| 파일 크기 | 85.8MB | 47.5MB |

| 비용 | 효과 | 잃는 것 |
| --- | --- | --- |
| 3~5일, 약 400줄 + 테스트 재작성(저장소 계층 테스트 대부분), 이전 명령, 백업을 `sqlite3`의 `backup()` API로 변경 | 조회·수정이 건수와 거의 무관해짐. 100만 건 이상에서도 체감 지연 없음. 원자성은 SQLite의 저널링이 보장 | 텍스트 편집기로 직접 열어 고칠 수 없음. "손상된 줄만 건너뛰고 보존" 같은 줄 단위 복구가 사라짐(파일 전체 무결성은 SQLite가 관리). 이 과제의 "JSONL 또는 CSV로 저장" 요구사항을 벗어남 |

> SQLite는 과제 요구사항(JSONL/CSV 저장) 밖이라 **학습용 확장 과제**로만 권합니다. 실제 서비스라면 50만 건을 넘기 전에 가장 먼저 검토할 선택지입니다.

| 거래 수 | 체감 상태 (측정) | 권장 | 누적 비용 | 기대 결과 |
| --- | --- | --- | --- | --- |
| ~10만 건 | 대부분 0.5초 이하, `update`/`delete` 0.7~0.9초. 조건 없는 `search`만 2초 | **현재 그대로**. D의 "limit 없는 search 기본 상한"만 추가 | 0.2일 | 모든 명령 1초 이하 |
| 10만~50만 건 | 조회 2초, 삭제 4초, 조건 없는 `search` 11초·787MB | **A + B + C + D** (JSONL 유지, 표준 라이브러리만) | 약 3~3.5일 | `add` 약 0.1s, 월 검색·요약 약 0.15s, `list --limit` 약 0.3s, `delete` 약 2s (모두 추정). 메모리는 모든 경로에서 100MB 이하 |

우선순위를 정한 근거는 **"비용 대비 효과"와 "자주 쓰는 명령"**입니다.

1. **A (0.5일, `add` 18배)**: 가장 자주 쓰는 명령이 가장 싸게 빨라집니다.
2. **B (1일, 선택적 검색 20배)**: `summary`와 `search --month`는 매달 쓰는 명령입니다.
3. **D (1~1.5일, `list` 10배 + 메모리 1/4)**: 메모리가 터질 수 있는 유일한 경로를 막습니다.
4. **C (0.5일, 삭제·수정 1.8배)**: 싸지만 재작성 자체(2초)는 남으므로 효과에 한계가 있습니다.
5. **E**: 앞의 개선 후에는 디코드하는 줄 자체가 줄어 효과가 작으므로 마지막입니다.
6. **F/G**: 재작성 비용(전체 파일 다시 쓰기)이라는 구조적 한계를 없애는 유일한 방법이지만, 비용과 잃는 것이 큽니다.

## 왜 이렇게 설계했나

- **처음부터 최적화하지 않은 이유**: 과제의 핵심 목표는 "예외 상황에서도 데이터가 안전한 구조"와 "설명할 수 있는 설계"입니다.
  A·B·D는 모두 **파일 형식에 대한 가정**("이 프로그램이 쓴 줄은 형식이 일정하다")에 기댑니다. 가정을 늘릴수록 손 편집이나 손상에 약해지고, 테스트할 경우의 수가 늘어납니다.
  10만 건(개인 가계부로 수십 년치)까지는 현재 구조로 모든 명령이 1초 안팎이므로, 단순하고 안전한 쪽을 택했습니다.
- **그래도 스트리밍은 처음부터 한 이유**: 속도는 나중에 고칠 수 있지만, **메모리 초과는 프로그램을 죽입니다.**
  그래서 `list`, `summary`, `update`, `delete`는 처음부터 건수와 무관한 메모리(22MB)로 동작하게 만들었습니다.
- **측정 먼저, 개선은 그다음**: "JSON이 느리니 CSV로 바꾸자"는 직관은 측정해 보면 효과가 8%에 그칩니다.
  진짜 병목(객체 생성 64%, 중복 훑기, 전체 재작성)은 재 보기 전에는 보이지 않습니다.

## 자주 하는 실수

- **형식만 바꾸면 빨라진다고 믿기**: 측정해 보면 JSONL → CSV는 8%입니다. 병목은 형식이 아니라 "필요 없는 줄을 객체로 만드는 일"입니다.
- **선필터를 최종 판단으로 쓰기**: bytes 비교는 후보를 줄이는 용도입니다. 디코드한 뒤 원래 조건으로 다시 검사하지 않으면, 우연히 같은 바이트열이 메모에 들어 있는 줄이 결과에 섞입니다.
- **놓치는 줄이 생기는 선필터**: 오탐(후보에 섞인 줄)은 최종 검사가 걸러 주지만, 누락(걸렀어야 할 줄을 버림)은 아무도 되살리지 못합니다. 선필터는 반드시 "누락 없음" 쪽으로 설계합니다.
- **평균만 보기**: `--limit` 없는 `search`처럼 드물게 쓰지만 787MB를 쓰는 경로가 프로그램을 죽입니다. 최악의 경로를 따로 재야 합니다.
- **따뜻한 캐시로만 재기**: 위 숫자는 운영체제 캐시가 데워진 상태입니다. 재부팅 직후 첫 실행은 디스크에서 읽어 더 느릴 수 있습니다. 비교할 때는 같은 조건에서 여러 번 재고 최솟값이나 중앙값을 씁니다.
